## 0. Propósito e Escopo

### Por que este documento existe

O `02_MASTER_IMPLEMENTATION_PLAN.md` (Fase 4, EOS-003) prevê a criação de templates HTML base em `05_IMPLEMENTACAO/design_system/templates/`. Porém, o `03.1_DESIGN_SYSTEM_SPECIFICATION.md` — a Fonte da Verdade estética — opera como um manual de direção de arte e filosofia, definindo *como pensar* sobre design, não *quais componentes HTML* devem existir.

Esta RFC preenche essa lacuna, derivando componentes implementáveis exclusivamente dos princípios já documentados na fundação da marca, sem inventar regras, tokens ou decisões estéticas novas.

### O que este documento NÃO é

- Não é uma biblioteca de UI.
- Não é uma especificação de páginas finais.
- Não é uma extensão do `tokens.css` (nenhum token novo é criado).
- Não é um sistema de componentes reutilizáveis no sentido de framework.

### Hierarquia de Autoridade (Herdada do 03.1, Seção 0)

Em caso de conflito, prevalece:
1. Brand Foundation (01–10)
2. Source of Truth Audit (EOS-000)
3. Design System Specification (03.1)
4. **Esta RFC (03.3)** — derivada do nível 3
5. Implementação (05)

## 1. Metodologia de Derivação

Cada componente proposto nesta RFC é derivado por rastreabilidade direta a um ou mais trechos dos documentos oficiais. A lógica é:

1. Identificar um **princípio documentado** que implique uma estrutura HTML.
2. Verificar se esse princípio possui **tokens CSS correspondentes** no `tokens.css` (EOS-002).
3. Verificar se algum **agente do pipeline** (04) necessita consumir ou produzir esse componente.
4. Se todas as condições forem atendidas, o componente é especificado.

Se alguma condição não for atendida, o componente não é proposto.

## 3. Especificação Individual dos Componentes

### 3.1 section-base

#### Objetivo
Materializar a "Fundação Invisível" (03.1, §8) como uma estrutura HTML semântica que define onde o conteúdo repousa e onde o espaço existe como "pausa musical" (03.1, §10).

#### Responsabilidade
- Fornecer a planta-baixa estrutural mínima para que o Designer Agent e o Coder Agent organizem a arquitetura da informação dentro de um bloco de contenção.
- Demonstrar o uso dos tokens de espaçamento (`--spacing-tight`, `--spacing-base`, `--spacing-large`, `--spacing-massive`) em contexto real.

#### Estrutura HTML Esperada

```html
<section>
  <header>
    <!-- Zona de título: font-primary, peso pesado -->
  </header>
  <div>
    <!-- Zona de conteúdo: font-secondary, peso regular -->
  </div>
</section>
```

#### Tokens CSS Obrigatórios
- `--color-base-black` ou `--color-base-offwhite` (fundo)
- `--color-base-offwhite` ou `--color-base-black` (texto, inverso do fundo)
- `--font-primary` (títulos)
- `--font-secondary` (corpo)
- `--spacing-massive` (margem externa — "Tensão Proporcional", §8)
- `--spacing-base` (padding interno)

#### Restrições
- Nenhum `border-radius` diferente de `--radius-square`.
- Nenhuma sombra (proibida conforme tokens.css, nota sobre shadows).
- Nenhum framework CSS (Flexbox, Grid) a menos que estritamente necessário para o alinhamento matemático descrito no §8. Caso utilizado, deve ser documentado como decisão técnica, não estética.
- Nenhuma media query ou breakpoint (o documento 03.1 não especifica comportamento responsivo para seções).

#### Anti-Patterns (Derivados de 03.1, §23 e 03, §8)
- Cantos arredondados.
- Sombras suaves, gradientes polidos ou glassmorphism.
- Centralização excessiva e simétrica ("layout padrão e preguiçoso", 04 §3.4.12).
- Preenchimento sem propósito que elimine o "Vazio Ativo" (04, §3.4.11).

#### Agentes Consumidores
- **Designer Agent** (04, §3.4): Utiliza como a base para definir hierarquias espaciais no Blueprint. O §3.4.3 diz: "Selecionar os componentes modulares corretos (do Design System)".
- **Coder Agent** (04, §3.8): Implementa o HTML final. O §3.8.6 Input Contract especifica: "documentos (...) os arquivos base de `tokens.css`".

### 3.2 typography-specimen

#### Objetivo
Materializar as 3 camadas tipográficas definidas no 03.1, §11: "A Estrutura" (Space Grotesk), "O Corpo" (Inter) e "A Intervenção" (Experimental), demonstrando a escala desde `--font-size-xs` até `--font-size-h1-colossal`.

#### Responsabilidade
- Servir como artefato de validação técnica para o Art Director Agent verificar que a hierarquia tipográfica está correta antes de formular Creative Briefs.
- Permitir que o Vision Agent audite a renderização tipográfica conforme o 03.1.

#### Estrutura HTML Esperada

```html
<article>
  <section>
    <!-- Camada 1: A Estrutura (font-primary) -->
    <h1><!-- font-size-h1-colossal, font-weight-heavy --></h1>
    <h2><!-- font-size-h2 --></h2>
    <h3><!-- font-size-h3 --></h3>
  </section>

  <section>
    <!-- Camada 2: O Corpo (font-secondary) -->
    <p><!-- font-size-body, font-weight-regular --></p>
    <small><!-- font-size-xs --></small>
  </section>

  <section>
    <!-- Camada 3: A Intervenção (font-experimental) -->
    <!-- "Nunca é usada para leitura contínua. É tratada como imagem, como arte" (03.1, §11) -->
    <div><!-- font-experimental, font-size-h1-colossal --></div>
  </section>
</article>
```

#### Tokens CSS Obrigatórios
- `--font-primary` (Space Grotesk)
- `--font-secondary` (Inter)
- `--font-experimental` (system-ui fallback)
- `--font-size-xs`, `--font-size-body`, `--font-size-h3`, `--font-size-h2`, `--font-size-h1-colossal`
- `--font-weight-regular`, `--font-weight-heavy`
- `--color-base-black`, `--color-base-offwhite`

#### Restrições
- A Intervenção (camada 3) não deve ser apresentada como texto de leitura corrida. O 03.1 §11 é explícito: "Ela **nunca** é usada para leitura contínua. É tratada como imagem, como arte".
- Nenhum peso tipográfico intermediário. O 03.1 §18 e o tokens.css definem apenas `400` e `800`. O 04, §3.4.11 reforça: "Jamais utilizar pesos tipográficos 'médios' que gerem monotonia".

#### Anti-Patterns
- Pesos intermediários (500, 600, 700).
- A Intervenção usada como corpo de texto.
- Hierarquias visuais onde subtítulos competem com títulos (04, §3.4.12).

#### Agentes Consumidores
- **Art Director Agent** (04, §3.3): Decide a "linguagem primária de impacto visual" (§3.3.3) utilizando as camadas tipográficas como referência.
- **Designer Agent** (04, §3.4): Define a "hierarquia tipográfica exata (Space Grotesk colossal vs Inter funcional)" (§3.4.3).
- **Vision Agent** (04, §3.9): Audita a "fidelidade entre o que foi planejado visualmente (...) e o que foi de fato renderizado" (§3.9.1).

### 3.3 block-component

#### Objetivo
Materializar a filosofia de componentes do 03.1, §18: "Componentes de interface (botões, cards, divisórias) são tratados como blocos de concreto. Eles são utilitários, sólidos, quadrados (border-radius 0 na maioria das vezes). A beleza do componente não está no seu arredondamento ou sombra, mas na sua solidez bruta."

#### Responsabilidade
- Fornecer a planta-baixa estrutural de um bloco de concreto que pode ser instanciado como botão, card ou divisória pelo Coder Agent, dependendo do contexto narrativo e do Blueprint do Designer Agent.
- Demonstrar que a solidez visual nasce dos tokens, não de adornos.

#### Estrutura HTML Esperada

```html
<!-- Variante: Botão -->
<button type="button">
  <!-- Texto utilitário em font-secondary -->
</button>

<!-- Variante: Card -->
<article>
  <header>
    <!-- Título em font-primary -->
  </header>
  <div>
    <!-- Conteúdo em font-secondary -->
  </div>
</article>

<!-- Variante: Divisória -->
<hr />
```

#### Tokens CSS Obrigatórios
- `--color-base-black` (fundo do bloco)
- `--color-base-offwhite` (texto interno)
- `--radius-square` (cantos retos obrigatórios)
- `--spacing-base` (padding interno)
- `--spacing-tight` (margem entre elementos internos)
- `--font-secondary` (texto utilitário de botão)
- `--font-primary` (título de card)
- `--font-weight-heavy` (ênfase)

#### Restrições
- Cantos estritamente quadrados. O 03.1, §18 define "border-radius 0 na maioria das vezes".
- Sem sombras. O tokens.css não define tokens de sombra, e o 03.1, §18 diz: "A beleza do componente não está no seu arredondamento ou sombra".
- Sem gradientes ou glassmorphism (03.1, §13: "Ausência total de glassmorphism").
- O componente é inerte: sem JavaScript, sem hover effects, sem animações (restrição explícita do EOS-003).

#### Anti-Patterns (Derivados de 03.1, §23)
- Botões com cantos super arredondados (§23.1: "Estética SaaS e Startup").
- Cores pastéis tranquilizantes (§23.1).
- Sombras suaves tipo material design.
- CTAs neon ou botões pulsantes (§23.4: "Hiper-Corporativismo").

#### Agentes Consumidores
- **Designer Agent** (04, §3.4): "Selecionar os componentes modulares corretos (do Design System) para hospedar o conteúdo" (§3.4.3).
- **Coder Agent** (04, §3.8): Implementa os componentes respeitando "unicamente os Design Tokens CSS definidos" (§3.8.3).
- **Brand Guardian** (04, §3.1): Audita se os componentes não ferem os anti-patterns absolutos (§3.1.12).

### 3.4 color-contrast

#### Objetivo
Materializar a filosofia cromática do 03.1, §12: demonstrar o contraste entre "Preto Profundo (#0E0F12)" e "Off-White Quente (#F3EDE3)" como os dois únicos valores de base documentados, funcionando como "o asfalto e a tela em branco".

#### Responsabilidade
- Servir como artefato de validação técnica da inversão cromática (dark-on-light e light-on-dark).
- Permitir que o Brand Guardian e o Vision Agent confirmem que o contraste base está corretamente implementado.

#### Estrutura HTML Esperada

```html
<div>
  <!-- Modo Claro: fundo offwhite, texto black -->
  <section>
    <h2><!-- font-primary --></h2>
    <p><!-- font-secondary --></p>
  </section>

  <!-- Modo Escuro: fundo black, texto offwhite -->
  <section>
    <h2><!-- font-primary --></h2>
    <p><!-- font-secondary --></p>
  </section>
</div>
```

#### Tokens CSS Obrigatórios
- `--color-base-black`
- `--color-base-offwhite`
- `--font-primary`
- `--font-secondary`
- `--spacing-large` (separação entre os blocos)

#### Restrições
- Apenas os dois valores cromáticos documentados. Nenhuma cor de acento é introduzida (o 03.1, §12 menciona cores vibrantes mas sem HEX explícito, e o tokens.css não os define).
- Sem gradientes entre os blocos.

#### Anti-Patterns
- Cores pastéis, gradientes suaves ou tons intermediários (03.1, §23.1).
- Minimalismo genérico que apague a tensão entre preto e off-white (03.1, §23.3).

#### Agentes Consumidores
- **Brand Guardian** (04, §3.1): Valida que os valores cromáticos utilizados são estritamente os documentados.
- **Vision Agent** (04, §3.9): Audita contraste de leitura e acessibilidade (03.1, §19: "Acessibilidade técnica (...) é inegociável").

## 4. Componentes Deliberadamente Excluídos

Os seguintes conceitos foram considerados durante a auditoria mas **não possuem respaldo documental suficiente** para se tornarem componentes base nesta RFC:

| Conceito | Motivo da Exclusão |
|---|---|
| `carrossel-base` | O 02_MASTER_IMPLEMENTATION_PLAN.md cita "ex: carrossel-base.html" como **exemplo ilustrativo**, não como especificação. O 03.1 não menciona carrossel. |
| `hero-base` | Inexistente na documentação 03.1 ou 03. Trata-se de um padrão de UI genérico sem respaldo na filosofia High House. |
| `grid-base` (como componente isolado) | O conceito de grid existe no §8 como "Fundação Invisível", mas sua função é ser invisível — não um componente exportável. A estrutura de grid é absorvida pelo `section-base`. |
| `navigation` / `menu` | O 03.1, §17 menciona que "Barras de navegação podem ser invertidas, menus escondidos atrás de tipografias monumentais", mas isso é uma diretriz de layout para o Designer Agent, não uma especificação de componente base. |
| `texture-overlay` | O 03.1 menciona texturas (§13), `mix-blend-mode` e `filter` (§20), mas estes são efeitos CSS para o Coder Agent aplicar contextualmente, não componentes base estáticos. |
| `showcase` | Não existe na documentação oficial. Será substituído por um `render_test.html` — artefato de validação técnica, assim como feito no EOS-002, mantendo consistência com o padrão existente. |

## 5. Artefato de Validação Técnica

Assim como o EOS-002 produziu um `render_test.html` para validar os tokens CSS, o EOS-003 produzirá um arquivo equivalente que agrupa os 4 componentes para inspeção visual em navegador.

**Este arquivo NÃO faz parte do Design System.** Trata-se exclusivamente de uma ferramenta de validação técnica, seguindo o precedente do EOS-002.

- **Arquivo:** `05_IMPLEMENTACAO/design_system/templates/render_test.html`
- **Função:** Carregar todos os templates e o `tokens.css` para verificação de renderização.
- **Não deve ser referenciado** por nenhum agente como componente do sistema.

## 6. Relação com o Pipeline de Agentes

```text
Art Director Agent
  │ consulta typography-specimen e color-contrast para formular Creative Brief
  ▼
Designer Agent
  │ seleciona section-base e block-component para construir o Blueprint
  ▼
Coder Agent
  │ implementa o HTML final usando os templates como referência + tokens.css
  ▼
Vision Agent
  │ utiliza os templates como baseline para auditoria de renderização
  ▼
Brand Guardian
  │ utiliza os anti-patterns documentados nos templates para auditoria de essência
```

## 7. Regras de Evolução

1. **Novos componentes** somente podem ser adicionados a esta RFC se derivados de atualizações no `03.1_DESIGN_SYSTEM_SPECIFICATION.md` ou no `03_BRAND_DESIGN_FOUNDATION.md`.
2. **Novos tokens** necessários para um componente devem primeiro ser adicionados ao `tokens.css` (via atualização do 03.1), nunca inferidos diretamente no template.
3. Esta RFC herda a regra de evolução do 03.1 (§22): "Novas texturas, novas tags de xarpi e novas paletas entram no sistema (...) baseados nas coleções culturais e nas manifestações da cena que a marca vivencia."
