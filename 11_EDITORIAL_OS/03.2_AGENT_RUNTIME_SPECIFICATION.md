# 03.2 Agent Runtime Specification

## 1. Propósito
Este documento define a infraestrutura de execução, orquestração e runtime do High House Editorial Operating System (EOS). Enquanto o `04_AGENT_SPECIFICATIONS.md` dita a inteligência e os limites cognitivos de cada agente, o **03.2** define a máquina operacional: como os agentes são alocados em memória, o ciclo de vida, roteamento de estados, observabilidade, segurança e versionamento em um ambiente de produção profissional multiagente.

## 2. Framework Decision & LLM Provider Abstraction
A stack oficial de orquestração do EOS é baseada em:
- **LangGraph:** Responsável pela orquestração do fluxo de trabalho. Define o grafo de execução (DAG), os nós (agentes), as arestas condicionais (transições) e o controle de interrupções.
- **LangChain:** Responsável pelas abstrações de ferramentas (Tools) e integrações. Atua como a ponte de padronização entre o grafo e o modelo.
- **LLM Provider Abstraction:** O EOS **não é acoplado** a um modelo específico. A arquitetura exige uma interface abstrata (ex: `BaseChatModel` do ecossistema) para invocar LLMs. 
  - *Implementação Atual:* **DeepSeek** (integrado via API nativa configurada no `.env`). Caso haja necessidade técnica, a troca do provedor exigirá apenas a alteração na factory de injeção, preservando o grafo intacto.

## 3. Runtime Architecture
A arquitetura modela o EOS como um **State Graph** gerido pelo LangGraph, seguindo estritamente princípios de Clean Architecture.

### 3.1. Thin Nodes & Injeção de Dependência
Os nós do LangGraph não devem conter lógica de domínio, instanciação de DTOs nativos ou hardcoding de Mocks. Eles atuam exclusivamente como **Thin Adapters** (Costuras):
- **Class-based Workflows:** A orquestração do grafo deve ser encapsulada em uma Classe (ex: `class EditorialWorkflow`).
- **Injeção de Interfaces:** As dependências (Interfaces dos Agentes e Serviços) devem ser injetadas no construtor (`__init__`) desta classe.
- **Node Methods:** Os nós do grafo são métodos da classe (`def _editorial_node(self, state)`) que apenas extraem dados do estado, repassam para a interface injetada, e devolvem a mutação para o estado global. Isso garante 100% de testabilidade isolada.

### 3.2. Topologia do Grafo
- **Nós (Nodes):** Cada agente descrito no `04` é acionado por um método adaptador da classe do workflow.
- **Arestas (Edges):** Condições lógicas de roteamento gerenciadas por Policies separadas (ex: `GuardianDecisionPolicy`).

## 4. State Schema Architecture
O estado global (ex: `GraphState`) é a única fonte de verdade transitada (Zero-Chat). O contrato oficial do estado do LangGraph é particionado rigidamente em 5 grupos:
- **Dados Imutáveis:** Parâmetros da run atual (`execution_id`), diretrizes de marca globais carregadas no boot (`brand_guidelines`), e `Design Tokens`. Eles não podem ser sobrescritos pelos agentes.
- **Dados Temporários (Transient):** Rascunhos de pesquisa (`raw_research`), contexto do usuário e variáveis de controle de fluxo de máquina (ex: `loop_count`).
- **Artefatos Produzidos (Payloads):** Os entregáveis concretos formatados (`curated_package`, `editorial_script`, `design_blueprint`, `html_code`).
- **Relatórios de Auditoria:** Feedbacks estruturados gerados pelos nós validadores (logs do Vision Agent, Critic Agent, Brand Guardian).
- **Memória Gerada:** Aprendizados e decisões finais que o Memory Agent serializará e persistirá no fechamento do ciclo.

## 5. Agent Communication & Lifecycle Management
O EOS opera de forma assíncrona e isolada, baseada puramente na leitura e mutação do State.

### 5.1. Agent Lifecycle
Durante a orquestração do Grafo, o nó (Agente) transita obrigatoriamente pelos seguintes estados:
- **Created:** Instanciado em memória, aguardando resolução das dependências do seu *Input Contract*.
- **Ready:** *Input Contract* satisfeito pelo `GraphState`. Acionado pelo runtime para rodar.
- **Running:** Em processamento ativo de rede junto ao LLM Provider.
- **Waiting Approval:** Interrompido pelo framework aguardando input humano (Human-in-the-loop).
- **Completed:** Execução bem-sucedida. `GraphState` foi atualizado em conformidade com o *Output Contract*.
- **Failed:** Falha crítica capturada durante a execução.
- **Recovered:** Estado recuperado após retry automático ou injeção corretiva.

## 6. Human-in-the-loop Architecture
Para garantir segurança corporativa e de marca, o runtime é configurado com interrupções automáticas (breakpoints do LangGraph) antes de transições críticas:
- **Brand Guardian Node:** Pode sinalizar interrupção de fluxo se detectar violação grave da essência, congelando o estado e aguardando override humano.
- **Vision Agent Node:** Interrompe a execução após a falha do limite máximo de loops com o Coder Agent, exigindo inspeção humana do layout quebrado.
- **Publish Node / Critic Agent:** (Configurável) Interrompe a publicação final para aprovação estratégica da campanha pela direção antes do *commit/deploy*.

## 7. Error Handling Architecture
O runtime intercepta exceções e as classifica oficialmente, definindo o comportamento de recuperação:
- **Business Error:** Violações de regras de marca ou rejeições semânticas (ex: Curator aprova conteúdo stoner). *Ação: Roteia o estado via Edge de volta ao nó gerador, injetando o log de erro para refazer o trabalho (limitado a X loops).*
- **Agent Error:** O agente falhou em estruturar o JSON/YAML, errou a assinatura de uma ferramenta ou sofreu alucinação de parser. *Ação: Aciona abstração de Retry automático no próprio nó (ex: LangChain Output Fixing Parser).*
- **Infrastructure Error:** Timeout da API do LLM, MCP indisponível ou falha de disco. *Ação: Suspensão segura da run, salvamento instantâneo do checkpoint do estado, alerta de falha e espera por intervenção de infra (Manual Retry).*
- **Quality Error:** Defeito visual apontado no código (Vision). *Ação: Roteamento de QA (Loop com o Coder Agent).*

### 7.1. Anti-Pattern: Mock Fallbacks em Produção
É expressamente **proibido** utilizar instâncias de Mock como mecanismo de "fallback" (ex: `try: real_agent() except: mock_agent()`) no runtime de produção. 
- Mocks existem única e exclusivamente para **Testes e Desenvolvimento Local**. 
- Eles devem ser injetados através da classe do Workflow (ver Seção 3).
- Se um agente real falhar em produção por instabilidade do LLM, isso é um `Infrastructure Error` e a execução deve ser suspensa com segurança, não mascarada por um texto estático gerado por mock.

## 8. Observability Layer
Nenhum nó opera como uma "caixa preta" silenciosa. A infraestrutura exige injeção de telemetria (via Callbacks) registrando estruturalmente:
- `execution_id` (UUID único da campanha/ciclo)
- `agent_id` (Identificador do nó ativo)
- `model_version` (Modelo consumido, ex: `deepseek-chat-v2`)
- `prompt_version` (Hash ou tag da versão do prompt no repositório)
- `timestamps` (Início, fim e latência de rede do provedor LLM)
- `decisions` (Rastreabilidade em JSON das lógicas assumidas pelo agente)
- `failures` (Stacktraces íntegros armazenados em caso de crash)

## 9. Runtime Security
A orquestração defende o ambiente host implementando blindagem e privilégio mínimo:
- **Isolamento de Ferramentas (Tool Isolation):** Ferramentas são injetadas (bind) unicamente nos nós autorizados. (Ex: O Coder Agent não possui a tool de Web Search; o Editorial Agent não tem a tool de Playwright).
- **Controle de MCPs e Permissões:** Servidores MCP operam via STDIO restrito. Acesso a filesystem via MCP é limitado por `CWD` e pastas permitidas na inicialização, impedindo vazamentos para fora da arquitetura do projeto.
- **Limites de Execução (Execution Limits):** Proteção contra *token burnout* estabelecendo `max_recursions` e controle de limite de *loops* no grafo (evitando que o Coder e o Vision fiquem rodando eternamente).

## 10. Execution Lifecycle (Pipeline Topology)
A topologia oficial de execução de uma campanha flui ciclicamente pelas camadas de infraestrutura detalhadas acima:
Input ➔ Research Agent ➔ Curator Agent ➔ Editorial Agent ➔ Brand Guardian ➔ Designer ➔ Coder ➔ Critic ➔ Memory Update.
