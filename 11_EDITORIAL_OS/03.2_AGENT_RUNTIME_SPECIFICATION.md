# 03.2 Agent Runtime Specification

## 1. Propósito
Este documento define a infraestrutura de execução, orquestração e runtime do High House Editorial Operating System (EOS). Enquanto o `04_AGENT_SPECIFICATIONS.md` dita a inteligência e os limites cognitivos de cada agente, o **03.2** define como a máquina gira: como os agentes são alocados em memória, como o estado flui entre eles, e como o ciclo de vida da execução é controlado.

## 2. Framework Decision
A stack oficial de orquestração do EOS é baseada em:
- **LangGraph:** Responsável pela orquestração do fluxo de trabalho. Define o grafo acíclico/cíclico (DAG), os nós (agentes), as arestas (transições de estado) e o controle de interrupções (Human-in-the-loop).
- **LangChain:** Responsável pelas abstrações de ferramentas (Tools), Memory e integrações. Atua como a ponte entre o grafo e o modelo.
- **DeepSeek:** Modelo LLM central para raciocínio e geração, integrado via API nativa configurada no `.env`.

*Justificativa:* O uso de LangGraph garante que o sistema possua estado persistente, capacidade de recuperação de falhas (checkpoints) e previsibilidade de execução, abandonando a aleatoriedade de "chains" simples para abraçar um fluxo de máquina de estados controlada.

## 3. Runtime Architecture
A arquitetura de execução modela o EOS como um **State Graph**.
- **Nós (Nodes):** Cada agente descrito no `04` é um nó independente no grafo.
- **Arestas (Edges):** As condições de roteamento. O sucesso da execução de um nó transita o estado para o nó subsequente.
- **Interrupções (Checkpoints):** O runtime pode pausar em nós críticos (ex: *Critic Agent* ou *Vision Agent*) para aprovação ou injeção humana antes de prosseguir.

## 4. Agent Communication Model
O modelo de comunicação do EOS possui **Zero-Chat**. Agentes não conversam entre si por mensagens livres.
- **State Propagation:** Os agentes recebem o `State` global do LangGraph, efetuam o processamento e devolvem um dicionário (update de estado) contendo estritamente os seus artefatos definidos no *Output Contract* do documento 04 (ex: `Curated_Package`, `Design_Blueprint`).
- O runtime garante que um agente só seja executado quando os dados requeridos no seu *Input Contract* estiverem validados no estado.

## 5. State Management
O estado do grafo (`TypedDict` ou análogo) é a única fonte da verdade durante a execução de um ciclo editorial.
- **Estado Global do EOS:** Contém as diretrizes imutáveis (`Brand Essence`, `Design Tokens`).
- **Estado Temporário de Execução:** Variáveis mutáveis durante o ciclo (Raw Data, Drafts, Blueprints).
- **Recuperação de Falhas:** O uso de Checkpoints (via `MemorySaver` do LangGraph) permite que um ciclo que falhou no Coder Agent seja retomado sem precisar rodar a Fase 1 novamente.

## 6. Memory Integration
- O runtime se comunica com o **Memory Agent** como um serviço auxiliar de I/O.
- Ao fim do ciclo, um nó terminal (`Memory Update`) extrai as decisões finais do State e invoca a integração de armazenamento local (`Decision Log`, `Experiment Memory`) para persistir o aprendizado.

## 7. Tool Architecture
- Ferramentas externas (Fetch, Browser, Playwright) são encapsuladas como *LangChain Tools* e acopladas aos nós (agentes) específicos.
- O runtime restringe o acesso às ferramentas com base na autoridade do agente (ex: o Designer Agent não tem acesso ao MCP Browser).

## 8. Execution Lifecycle (Pipeline)
A execução de um *Release* no EOS segue estritamente a topologia abaixo no LangGraph:

1. `[START]` ➔ Inicialização do State com Briefing
2. `[NODE]` ➔ **Research Agent** (Exploração Divergente)
3. `[NODE]` ➔ **Curator Agent** (Filtro Convergente)
4. `[NODE]` ➔ **Editorial Agent** (Escrita do Script)
5. `[NODE]` ➔ **Brand Guardian** (Validação de DNA)
6. `[NODE]` ➔ **Art Director & Designer** (Blueprint Visual)
7. `[NODE]` ➔ **Coder & Image** (Materialização Concorrente)
8. `[NODE]` ➔ **Vision Agent** (QA Técnico - *Loops permitidos*)
9. `[NODE]` ➔ **Critic Agent** (Auditoria Qualitativa)
10. `[NODE]` ➔ **Memory Update** (Fechamento do Ciclo)
11. `[END]`
